# Go 语言档案（L1）

> 配套 `../REVIEW_RULES.md`（L0 通用方法论）。本文件只管"在 Go 里什么算缺陷、什么算误报"。

---

## 1. 适用范围与版本约束

| 要确认 | 从哪看 | 影响什么 |
|---|---|---|
| Go 版本 | `go.mod` 的 `go` 指令 | **1.22 起循环变量每次迭代新建**，之前是共享的——这条直接决定一类经典 bug 存不存在 |
| 泛型 | 版本 ≥ 1.18 | 低于 1.18 不能用类型参数 |
| 并发模型 | 有无 `sync` / `channel` / `errgroup` | 决定"加锁"是不是对的建议 |

**`go.mod` 里写 `go 1.22` 之后，不要再提"循环变量捕获"**，那是老版本的坑。

## 2. 语言惯用法（判断"像不像问题"的前提）

- **错误是返回值，不是异常。** 每个可能失败的调用后面跟 `if err != nil` 是**惯用法**，不是啰嗦。
- **零值可用**是设计目标（`var m map[string]int` 是 nil，读可以、写 panic）。
- **并发用 channel 传数据、用 `sync` 保护状态**，两者是替代关系不是叠加关系。
- **`panic` 只用于程序错误**，正常失败路径用 `error` 返回。
- **接口是隐式实现**，不要建议加 `implements` 之类。

## 3. 常见确定性缺陷

### 3.1 忽略错误
- `err` 拿到了但没检查（`_ = f()` 除外，那是有意的）。
- `defer f.Close()` 的返回值被丢弃，而写入错误恰恰出现在 Close。
- goroutine 里的错误没人收 → 失败静默。

### 3.2 nil 相关
- **向 nil map 写入 → panic**（读不会）。`var m map[string]T` 之后直接 `m[k] = v`。
- nil 指针解引用、nil interface 调用方法。
- 返回了 `(*T)(nil)` 装进 interface，导致 `if x != nil` 判断为真（经典陷阱）。

### 3.3 并发
- **多 goroutine 无锁写同一变量 → 数据竞争**（`go test -race` 能查）。
- goroutine 泄漏：启动了但没有退出路径（channel 永远没人关）。
- `defer` 在循环内累积（要等函数返回才执行）。
- 闭包捕获循环变量（**仅在 go < 1.22 成立**）。

### 3.4 切片与 map
- 切片共享底层数组：`s2 := s1[:2]` 之后追加可能覆盖 `s1`。
- 循环里取 `&v` 拿到的是同一个地址（同样受 1.22 影响）。

## 4. 误报清单（★ 最常被误提的）

- ❌ **"这里没有 try/catch，异常会漏掉"** → Go 没有异常。有 `err` 返回值就不是漏。
- ❌ **"建议加锁"** 用在 channel 传递所有权的场景 → 并发模型选错了就会给错建议。
- ❌ **"建议把 error 改成 panic 更好定位"** → 违背 Go 的错误处理约定。
- ❌ **"`if err != nil { return err }` 太啰嗦，建议封装"** → 这是本项目/本语言的写法，P3 且通常不该提。
- ❌ **"循环变量捕获，闭包里拿到的是同一个变量"** → `go.mod` 声明 ≥ 1.22 时**已经不成立**。
- ❌ **"建议引入泛型重写"** → 设计偏好。
- ❌ **"建议用 ORM / 换框架"** → 超范围。
- ❌ **"`defer` 有性能损耗"** → 现代 Go 已优化，且这是 P3。
