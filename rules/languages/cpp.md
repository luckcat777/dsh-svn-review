# C++ 语言档案（languages/cpp.md）

> **L1 语言档案。** 适用条件：代码是 C / C++。
>
> 三层分工与优先级同 `java.md` 开头：**L2 项目约定 > 本文件 > L0 默认判断**。

---

## 1. 适用范围与版本约束

**先确认三件事，再开始审**：

1. **语言标准**：C++98/03、C++11、C++14、C++17 还是 C++20？
   - 常见误判来源：对 C++98 代码库建议 `auto`、`nullptr`、范围 `for`、`std::make_unique` —— 编译不过。
2. **异常是否开启**：很多游戏/嵌入式项目用 `-fno-exceptions`。
   - 若已关闭，一切"用异常做错误处理"的建议都是误报。
3. **RTTI 是否开启**：`dynamic_cast` 在 `-fno-rtti` 下不可用。

看 `CMakeLists.txt`、`*.vcxproj`、`Makefile` 里的 `-std=` / `CXX_STANDARD` / `<LanguageStandard>`，**不要假设**。

## 2. 语言惯用法（审查前必须理解）

| 惯用法 | 含义 | 审查含义 |
|---|---|---|
| 裸指针参数 | 通常**不拥有**所有权 | 不能因为"是裸指针"就判泄漏 |
| 返回裸指针 | 可能是工厂、可能是借用 | 必须看调用方是否 `delete` |
| 错误码返回值 | 项目可能禁用异常 | 检查是否被忽略，而不是要求抛异常 |
| `assert` 做参数校验 | 只在 Debug 生效 | Release 下等价于没检查——但改动 `assert` 不是本次 diff 的事 |

**C++ 的判据是"是否存在未定义行为（UB）或确定的资源错误"**，不是"是否符合现代 C++ 风格"。

## 3. 常见确定性缺陷（P1 候选）

### 3.1 悬垂（dangling）

| 模式 | 后果 |
|---|---|
| 返回局部变量的引用/指针 | 函数一返回就悬垂，读取即 UB |
| 保存 `vector` 元素的指针/迭代器后 `push_back` | 扩容导致全部失效 |
| lambda 按引用 `[&]` 捕获局部变量后逃逸（存入回调、异步） | 调用时栈帧已销毁 |
| `std::string` 的 `c_str()` 存起来越过作用域 | 指针悬垂 |
| `shared_ptr` 循环引用 | 永不释放（泄漏，非崩溃） |

### 3.2 内存

| 模式 | 后果 |
|---|---|
| `new[]` 配 `delete`（或反之） | UB，堆损坏 |
| 同一指针 `delete` 两次 | 堆损坏 / 崩溃 |
| 拷贝构造/赋值缺失（rule of three） | 浅拷贝 → 双重释放 |
| 基类析构非 `virtual`，经基类指针删除派生对象 | 派生类部分不析构，泄漏 |
| 构造/析构中抛异常 | 泄漏或直接 `terminate` |
| `memcpy` 源目标重叠 | UB，应用 `memmove` |

### 3.3 对象语义

| 模式 | 后果 |
|---|---|
| 按值传基类参数（slicing） | 派生部分被切掉，虚函数失效 |
| 成员未在构造函数初始化 | 内置类型成员值不确定（UB） |
| `struct`/`class` 有指针成员却用默认拷贝 | 浅拷贝 |
| 移动后继续使用源对象 | 状态未定义（不崩但结果错） |

### 3.4 数值与边界

| 模式 | 后果 |
|---|---|
| **有符号**整数溢出 | UB，编译器可假设不发生并据此优化 |
| 数组下标 `<=` 写成 `<` 的反面（off-by-one） | 越界读写 |
| `sizeof(ptr)` 当 `sizeof(array)` | 循环只处理前 8 字节 |
| 整数除零 | 崩溃（SIGFPE） |
| `unsigned` 与 `signed` 混比 | 负数被转成巨大正数 |
| `float`/`double` 直接 `==` 比较 | 精度导致永不相等 |

### 3.5 控制流

| 模式 | 后果 |
|---|---|
| 非 `void` 函数有分支没 `return` | UB（不是返回 0） |
| `switch` 缺 `break` | 贯穿到下一分支 |
| 循环里 `erase` 后继续用迭代器 | 迭代器失效 |

### 3.6 并发

- 无锁访问共享可变数据 = 数据竞争 = UB（即使"看起来只是读到旧值"）。
- 但**必须先证明存在并发访问**：单线程循环、初始化阶段、`main` 之前/之后都不构成。

## 4. 误报清单（不得提出的意见）

> 在 C++ 语境里，以下建议要么编译不过，要么把一种写法换成另一种写法而不解决可达性。

### 4.1 版本越界

- ❌ 建议 `auto`、`nullptr`、范围 `for`、`std::unique_ptr`、`std::make_shared`、`override`/`final`、`constexpr`、结构化绑定
  → 仅在目标标准支持时才成立，否则编译不过。先确认标准。
- ❌ 建议升级到 C++11/17
  → 不是本次 diff 的事。

### 4.2 风格伪装成缺陷

- ❌ 「建议全面改用智能指针」
  → 若项目有既定所有权约定、或裸指针出现在 ABI / 第三方接口上，改成 `unique_ptr` 会破坏接口。需指出**具体哪一次 `new` 没有对应释放**。
- ❌ 「建议加 `std::move`」
  → 对返回值加 `std::move` 会**阻止 NRVO**，是负优化；对 `const` 对象加 `std::move` 会静默退化为拷贝。
- ❌ 「建议给函数加 `noexcept`」
  → 不是缺陷。给移动构造标错 `noexcept` 会直接 `terminate`。
- ❌ 「建议用 `std::string` 替代 `const char*`」
  → 协议/序列化/ABI 边界上 `const char*` 往往是刻意的。
- ❌ 「建议用 RAII 管理这个资源」
  → 泛泛而谈不成立。必须指出**哪条异常路径**会泄漏。
- ❌ 「建议用 `std::atomic` / 加锁」
  → 必须先证明存在跨线程访问；单线程热路径上加原子操作是性能倒退。
- ❌ 「建议改用 `std::vector` 替代数组」
  → P3 偏好，看是否在热路径。

### 4.3 异常与错误处理

- ❌ 「这里没有异常处理，建议 `try-catch`」
  → 需确认项目开了异常；且必须指出具体异常类型与后果。
- ❌ 「建议用异常替代错误码」
  → 若 `-fno-exceptions`，这是编译不过的建议。

## 5. 提交前自检项

- [ ] 有没有返回局部变量的引用/指针？
- [ ] 保存的迭代器/指针，在使用前容器是否可能扩容或删除元素？
- [ ] 每个 `new`/`new[]` 是否有明确且匹配的释放路径（含异常路径）？
- [ ] 有指针成员的类，是否定义了拷贝构造/赋值/析构（或已 `= delete`）？
- [ ] 基类析构是否 `virtual`（若会被多态删除）？
- [ ] 所有成员是否在构造函数里初始化？
- [ ] 有符号整数运算是否可能溢出？下标是否可能越界？
- [ ] lambda 是否有按引用捕获的局部变量被带出作用域？
- [ ] 非 `void` 函数是否所有分支都有 `return`？
- [ ] 有没有提议超出目标标准的新语法？（有就删掉）
