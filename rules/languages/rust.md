## 1. 适用范围与版本约束

**审查前必须先确认这三件事**，结论不同：

| 要确认 | 从哪看 | 影响什么 |
|---|---|---|
| edition | `Cargo.toml` 的 `edition` | 2015/2018/2021/2024 的 `use` 路径、闭包捕获、`dyn` 写法都不同 |
| MSRV | `rust-version` 字段 | 决定能不能用 `let-else`(1.65)、`if let` 链、GAT 等 |
| 运行时 | 依赖里有无 `tokio`/`async-std` | 决定 `async` 相关建议是否成立 |

**不确定 edition 时不要提 `edition 2021` 才有的写法。**

## 2. 语言惯用法（判断"像不像问题"的前提）

- **失败用 `Result` / `Option` 表达**，`panic!` 属于"程序有 bug"，不是正常错误处理路径。
- **`unwrap()` / `expect()` 不是原罪。** 原型代码、测试、以及"逻辑上不可能失败"的地方用它是对的。
- **内存安全由编译器保证。** safe Rust 里不存在悬垂指针、double free、缓冲区溢出——提这些必然是误报。
- **所有权导致的问题**表现为编译错误，不会流到运行时。所以"这行会不会 use-after-free"在 safe 代码里没有意义。
- **`unsafe` 是有意的边界**，看到 `unsafe` 不等于看到缺陷，要看它内部的不变式。

## 3. 常见确定性缺陷

### 3.1 可达的 panic
- `unwrap()` / `expect()` 落在**输入驱动**的路径上（解析外部数据、查表、`HashMap` 索引）。
- 数组/切片下标 `v[i]` 未检查长度。
- 整数除法 / 取模未检查除数为 0。

> 判定要点：能不能说出"什么输入让这里 panic"。说不出来就是 P2。

### 3.2 整数溢出
- debug 构建 panic，release 构建静默回绕 → **同一份代码两种行为**。
- 涉及金额、计数、时间戳计算时，`as` 强转（`u64 as u32`）截断是真缺陷。

### 3.3 并发
- `std::sync::Mutex` 的 guard **跨 `.await` 持有** → 异步运行时下的死锁风险。
- `tokio::spawn` 里捕获了非 `'static` 引用（编译不过）或持有未释放的锁。
- 用 `Rc<RefCell<T>>` 跨线程传递（编译不过）；运行时 `RefCell` 双重 borrow → panic。

### 3.4 资源与生命周期
- `File`/`TcpStream` 忘记 `drop`（Rust 会自动 drop，所以这条通常**不成立**，除非用了 `mem::forget` 或 `Box::leak`）。
- `loop { spawn() }` 没有退出条件 → 任务无限增长。

## 4. 误报清单（★ 最常被误提的）

- ❌ **"这里可能内存泄漏 / 悬垂指针 / double free"** → safe Rust 编译期已排除。除非就在 `unsafe` 块内，否则一律误报。
- ❌ **"建议加锁保证线程安全"** → 先证明该数据确实跨线程共享（`Send + Sync`）。单线程或已用 channel 传递所有权的地方，加锁是错的建议。
- ❌ **"`unwrap()` 有风险，建议改成 `expect()`"** → 换一种 panic，不解决任何问题。
- ❌ **"建议改用 `Arc<Mutex<_>>`"** → 同上，需先证明有共享可变状态。
- ❌ **"`clone()` 太多，建议改引用"** → 借用检查器没拦说明可能本来就需要；这是性能偏好，P3。
- ❌ **"建议加 `#[inline]`"** → 编译器自己会决定。
- ❌ **"这个 `unsafe` 很危险，建议去掉"** → 需指出它违反了哪条不变式，否则是臆测。
- ❌ **"建议用 `?` 替代 `match`"** → 风格，P3，且有时 `match` 需要分别处理变体。
