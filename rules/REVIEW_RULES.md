# AI 代码审查规则 · 通用核心（REVIEW_RULES.md）

> **L0 通用方法论。** 与语言无关、与项目无关。
>
> 本文件只回答四个问题：**审哪里、多严重、要什么证据、怎么收尾**。
> 至于"在这门语言里什么算缺陷"，不在本文件，在语言档案里。

### 加载规则

1. 按变更集里**文件的扩展名**选语言档案：`.java`→java8、`.cpp/.h/.cc`→cpp、`.js/.ts/.mjs`→javascript、`.cs`→csharp。
2. 一个变更集里混了多种语言（如 Java 服务 + JS 前端），**每种语言各读一份**，分别套用各自的误报清单。
3. 没有对应语言档案时：只用 L0，并在报告里注明「无语言档案，未套用语言层豁免」——这会让你更容易误报，所以报告可信度要相应下调。
4. **冲突时优先级：L2 项目约定 > L1 语言档案 > L0 默认判断。**

## 0. 总纲

> **审查的目标是阻止"会造成线上事故的缺陷"，不是"把代码改到审查者满意"。**
>
> **无法举证的问题不是问题，只是猜想。猜想不得变成修改任务。**

三条推论，贯穿全文：

1. **举证责任在审查方。** 提出一个问题，就要给出触发路径和后果。给不出，自动降级。
2. **审查范围有边界。** 只审本次变更，不审历史代码，不审未触碰的文件。
3. **结论必须一次给完。** 禁止"发现一条 → 让开发改 → 再看下一条"的挤牙膏式审查。

## 1. 审查范围（Scope）

### 1.1 必须审
- 本次 diff 中**新增或修改的行**
- 这些行**直接调用的**函数/类（仅一层，用于确认签名、空值、返回语义）
- 与变更直接相关的：接口定义、数据 Key 新增、配置读取、跨服务/跨模块影响面

### 1.2 不得审
- 未改动的历史代码（哪怕写得很差）
- 整个文件的"整体风格"
- 依赖版本、构建脚本、数据库表结构（除非本次变更直接依赖其改动）
- 其他模块的既有问题

### 1.3 历史问题的处理
如果审查中发现**未被本次变更触碰的**历史缺陷：

> 写入报告末尾的「附录：范围外观察」，标注 `[范围外]`，**不阻塞、不计入问题数、不要求本次修复**。

### 1.4 变更集从哪来（★ 前置动作）

审查开始前，必须先拿到**变更集**，不得凭记忆或凭"整个文件"审查：

```powershell
E:\rules\ai_code_review_files\tools\run-audit.cmd
# 产物：reports/review-packet.md（自包含审查包）
```

- 详细原理与用法见 `SVN_WORKFLOW.md`。
- **变更集之外的文件，既不在审查范围，也不在修改范围。**
- 审查方不得要求开发方"顺便修一下"未在变更集内的文件（见 `SVN_WORKFLOW.md` §1.2）。

## 2. 问题分级（P0–P3）

| 级别 | 定义（语言无关） | 判定要点 | 处理方式 | 是否阻塞 |
|---|---|---|---|---|
| **P0** | 会造成线上事故：数据损坏、资产/资金错误、服务不可用、无法回滚 | 能说明"哪类用户、什么操作、坏成什么样" | 必须修复 | **阻断** |
| **P1** | 确定性缺陷：在已知输入/状态下**必然**出错 | 能证明该分支/状态可达，且现有防护拦不住 | 必须修复 | **阻断** |
| **P2** | 潜在问题：有真实风险，但需特定条件才触发，或影响有限 | 风险真实但无法证明必然发生 | 记录，开发方验证后决定 | 不阻断 |
| **P3** | 风格与偏好：命名、格式、注释、代码组织、可读性 | 换个写法同样能跑 | 最多合并为 1–2 条备注 | 不阻断 |

**各语言里"典型 P0/P1 长什么样"，见对应语言档案 §3。** 本文件不列举语言特有的例子，避免把某门语言的直觉当成通用标准。

### 分级校准规则

- **拿不准 P0 还是 P1 → 取低一级，按 P1 处理。**
- **拿不准 P1 还是 P2 → 取 P2。** （P1 要求"必然出错"，做不到必然性就是 P2）
- **同一个根因出现在多处** → 合并为 1 条，列出所有位置，不要拆成 N 条。
- **纯度问题**：一条意见里不得混装"P1 缺陷 + P3 重构建议"。

## 3. 举证责任（Evidence Requirement）★ 核心条款

提出 **P0 / P1** 时，必须同时给出以下四项，缺任意一项 → **自动降级为 P2，且不得要求本次修改**。

```text
① 触发路径：从哪个入口进来 → 什么输入/状态 → 走到第几行
② 前置条件：需要什么配置、什么数据状态、什么并发/时序
③ 后果：具体坏在哪（数据错 / 资产错 / 崩 / 卡死），影响面多大
④ 现有防护为何失效：代码里已有的判空、开关、队列、try-catch、类型系统为什么拦不住
```

### 语言无关示例

> **[P1]** `src/order/pricing.ext:142` — `applyDiscount` 里对 `memberLevel` 查表的结果未做存在性判断，直接取了 `[0]`。
> ① 触发路径：下单入口 `OrderService.create` → 计算价格 → `pricing.applyDiscount(order)` → 第 142 行查 `levelTable.get(memberLevel)` → 取第 0 项
> ② 前置条件：`member_level` 表缺该等级记录（运营新增等级但未同步配置表即可出现）
> ③ 后果：抛异常中断下单，用户支付成功但订单未生成；同一批次其他订单不受影响
> ④ 现有防护为何失效：`applyBasePrice`（:88）对同一张表做了判空，唯独这里直接取下标；上游 `create` 只校验了用户是否登录，没校验配置完整性

（`ext` 处按实际语言写 `.java` / `.cpp` / `.ts` / `.cs`。）

### 无效示例（一律按 P2 或直接丢弃）

| 常见表述 | 为什么无效 |
|---|---|
| "这里可能会空指针" | 没有调用路径，没有前置条件 |
| "建议加锁，保证线程安全" | 没有证明存在跨线程访问；单线程上下文里是错误判断 |
| "建议改成 `requireNonNull` 之类" | 只是换一种崩法，不解决 §3①③ |
| "建议拆分这个长方法" | P3，且不得在缺陷意见里夹带 |
| "建议补单元测试" | 需先确认项目有测试基建，否则不可执行 |
| "建议升级某依赖到新版本" | 依赖版本通常由框架组锁定，超出本次变更范围 |
| "这里没有异常处理" | 需指出具体异常类型与后果，否则不成立 |
| "不符合单一职责原则" | 设计偏好，非缺陷 |
| "如果并发调用会出问题" | 需给出"并发从哪来" |
| "这里可能 `undefined` / `null`" | 需给出哪条路径能让它为 `undefined`/`null`；已用空值传播语法的则不成立 |

> **判定口诀：说不出"谁会触发、在什么条件下、坏成什么样"，就不是问题。**

### 各语言的可举证形式

同一句"可能空指针"，在不同语言里的成立条件完全不同：

| 语言 | 成立条件 | 见 |
|---|---|---|
| Java 8 | `Map.get` / 链式调用返回 `null` 后直接调方法 | `languages/java8.md` §3.1 |
| C++ | 解引用空指针是 UB，但要看是否已有 `assert`/`not_null` 约定 | `languages/cpp.md` §3 |
| JS/TS | 若已用 `?.`/`??` 或 TS `strict`，多半不成立 | `languages/javascript.md` §3 |
| C# | 若已启用可空引用类型，编译器已保证 | `languages/csharp.md` §3.5 |

**这是最容易产生误报的地方：先用语言档案确认"这在该语言里算不算问题"，再决定要不要写进报告。**

## 4. 豁免清单（四层）

豁免 = **审查方不得提出的意见**。提出即视为误报，记入附录 A。

### 4.1 通用豁免（与语言、项目都无关）

- ❌ 未在变更集内的代码的任何问题 → 写入「范围外观察」，不阻塞
- ❌ 命名、格式、注释、空行、代码组织（P3 才谈得上，且不单独成条）
- ❌ "建议拆分长方法 / 提取类 / 重构"
- ❌ "建议补充单元测试"（除非已确认项目有测试基建）
- ❌ 依赖版本升级、构建工具替换
- ❌ "建议引入某个框架/库"
- ❌ 泛泛的架构建议（"应该分层"、"应该用 DDD"）

### 4.2 语言专属豁免

**由对应语言档案定义**，本文件不重复。

- Java 8 → `languages/java8.md` §4
- C++ → `languages/cpp.md` §4
- JavaScript/TypeScript → `languages/javascript.md` §4
- C# → `languages/csharp.md` §4

典型形态：对 Java 8 建议 `var`/`record`、对 C++98 建议智能指针、对 JS 建议加锁、对 C# 建议全面 `async` 化 —— 都是**语言层误报**。

### 4.3 项目专属豁免

**由对应项目档案定义。**

- x_main → `projects/x_main.md` §13

典型形态：并发模型是 actor 队列所以不需要锁、异常隔离是故意为之、协议载体字段名不能改、构建配置归框架组管。

### 4.4 已裁决豁免

- ❌ 任何在**附录 A 裁决记录**中已标注"豁免不修"的问题。
  → 审查方必须先读附录 A。重复提出已豁免项 = 严重误报。

### 4.5 冲突处理

| 情形 | 处理 |
|---|---|
| L1 说是误报，L2 说是缺陷 | 以 **L2** 为准（项目实际约定优先） |
| L2 说是误报，L1 说是缺陷 | 以 **L2** 为准 |
| 附录 A 已豁免，但 L1/L2 说这是新问题 | 以 **附录 A** 为准，除非开发方主动要求重新裁决 |
| 语言档案缺失 | 只用 L0，并在报告中声明 |

## 5. 输出格式（强制）

审查报告必须是以下结构，不得自由发挥：

```markdown
## 审查结论

**结论**：BLOCK / PASS_WITH_NOTES / PASS
**diff 覆盖率**：已完整检查本次变更的全部 N 个文件（是/否）
**加载的档案**：L1 = languages/java8.md；L2 = projects/x_main.md
**问题统计**：P0 = 0，P1 = 2，P2 = 3，P3 = 1

### 问题清单

| ID | 级别 | 位置 | 问题 | 证据（①②③④） | 建议 | 需本次修改 |
|---|---|---|---|---|---|---|
| R1 | P1 | `src/.../X.java:1823` | 查表结果未判空即取下标 | ①...②...③...④... | 加存在性判断 | 是 |
| R2 | P2 | `src/.../Y.java:210` | 高频路径内拼接大 JSON | ①...②...③... | 观察 | 否 |

### 附录：范围外观察（不阻塞、无需修改）
- [范围外] `src/.../Z.java:88` ...

### 附录：误报声明（如有）
- 撤回/降级说明
```

### 硬性约束

1. **P2 最多 5 条，P3 最多 2 条（且必须合并表述）。** P0/P1 不限。
2. 每条意见**只描述一个问题**，禁止夹带重构。
3. `证据` 列填不满 §3 的四项 → 该条**不得出现在 P0/P1 行**。
4. 必须回答「diff 覆盖率」。回答"否"时，本轮结论只能是 `PASS_WITH_NOTES`，不得 BLOCK（未看全就没资格阻断）。
5. **必须声明加载了哪些档案。** 没读语言档案却给语言相关意见，视为未举证。
6. 不得输出"整体建议""架构思考""进一步优化方向"等段落。

## 6. 审查结论规则

| 结论 | 触发条件 | 开发方动作 |
|---|---|---|
| `BLOCK` | 存在 ≥1 条通过 §3 举证的 P0/P1 | 修完再提 |
| `PASS_WITH_NOTES` | 仅有 P2/P3，或 diff 未完整覆盖 | 可提交；P2 自行登记验证 |
| `PASS` | 无问题 | 提交 |

**约束**：
- 同一轮只能给**一个**结论。
- **禁止增量阻断**：若本轮 `BLOCK`，下一轮必须基于"完整看过的 diff"给结论，不得又发现新的 P0/P1（若确实新发现，需说明为何上一轮漏看）。
- **禁止无举证 BLOCK**。

## 7. 争议裁决流程（终止无限返工的关键）★

审查意见不是命令。任何一条意见都可以被裁决。

```text
审查方提出意见
      ↓
开发方判断
      ├─ 认同 → 修改 → 记录到附录 A（结论：已修）
      ├─ 不认同 → 提交「反证」：
      │      ① 该路径不存在 / 已被上游拦住（给出代码位置）
      │      ② 该状态在本项目中不可达（引用 projects/<项目>.md 章节）
      │      ③ 该风险已被明确接受（给出设计说明 + 理由）
      │      ④ 该问题不在本次 diff 范围
      ↓
裁决（人 / 项目负责人，或按 §7.2 自动规则）
      ├─ 修改
      ├─ 豁免不修 → 写入附录 A
      └─ 留下轮（写入附录 A，标注"待办"）
      ↓
附录 A 生效：后续任何一轮审查，不得再提同一问题
```

### 7.1 反证的三条铁律
- 反证必须落到**代码位置或文档章节**，不能只写"我认为没问题"。
- 反证成功后，该条意见**当场作废**，审查方不得换个说法重复提出。
- 反证失败 → 按原级别修。

### 7.2 自动裁决规则（无需人工介入）
| 情形 | 自动结论 |
|---|---|
| 意见属于 §4.1/§4.2/§4.3 任一层豁免 | **直接豁免**，不修，记入附录 A |
| 意见为 P2/P3 且开发方给出了未采纳理由 | **豁免**，记入附录 A |
| 意见无法给出 §3 的 ①②③④ | **降级为 P2**，不修 |
| 意见指出的是未改动行 | **范围外**，不修 |
| 意见与附录 A 已豁免项相同或等价 | **视为误报**，记入附录 A 并提示审查方 |

## 8. 开发方提交前自检清单（给写代码的 AI）

在提交/发起审查前，**用本文件 + 语言档案 + 项目档案对本次 diff 自检一遍**，把 P0/P1 自己先修掉。自检结果写进提交说明。

**通用部分（每次都要过）：**

- [ ] 本次 diff 有没有引入必然出错的分支（可证明的越界、空引用、类型错误）？
- [ ] 有没有"改了这个、忘了改那个"的连带遗漏（同名字段、同类分支、成对的方法）？
- [ ] 变更集之外的文件有没有被顺手改动？（有就还原）
- [ ] 新增的错误处理，是否真的覆盖了出错的那一行？
- [ ] 有没有把"看起来不对"当成"确实不对"，改掉了别人的设计？

**语言部分**：见 `languages/<语言>.md` §5 的自检项。

**项目部分**：见 `projects/<项目>.md`（x_main → §13 豁免清单）。

## 附录 A：裁决记录（追加式，只增不改）

> **审查方必须先读完本表再开始审查。**
> 同一问题（或等价问题）已被裁决的，不得在后续任何一轮审查中再次提出。

## 附录 B：演进机制

本文件不是一次性产物，随争议持续完善：

- **每次裁决后**：把结论追加进附录 A。这是防止返工的**唯一硬保障**。
- **新语言接入**：复制一份最接近的语言档案改写，重点是先写**误报清单**（第 4 节），而不是先写缺陷清单——误报才是这套流程真正的成本。
- **每月复盘**：统计哪些问题被反复提出但被裁决豁免 → 补进对应层的豁免清单（语言问题进 L1，项目问题进 L2）。
- **误报率指标**：`误报数 / 总意见数`。目标 **< 15%**。超过则收紧 §3 举证门槛（宁少勿滥）。
- **漏报容忍**：宁可漏掉一个 P2，也不要制造十个误报。开发者注意力是最稀缺的资源。

> 自动化代码审查的工程共识是**精确率优先于召回率**：低价值评论会训练开发者忽略所有评论，包括真正致命的那条。
