# 审查指令模板（PROMPT.md）

> **本文件是"你该怎么说"，不是"AI 该怎么做"。**
> 规范分层：`REVIEW_RULES.md`（L0 怎么评）、`languages/<语言>.md`（L1 这门语言什么算缺陷、什么是误报）、`projects/<项目>.md`（L2 项目为什么不能那样改）、`SVN_WORKFLOW.md`（L0 能改哪里）。
>
> **每条命令都是完整的，直接复制一整块发出去即可，不需要拼接。**
> 所有命令的共同前提：**只处理 SVN 中已经修改的代码，不改动其他文件。**

---

## 0. 前置：拿到变更集和语言档案

两种方式，装了插件优先用第一种：

**① 装了 `dsh-svn-review` 插件**（推荐，能自动认出语言和版本）

```
调用 project_profile（不带参数，默认当前目录）
→ 拿到 languages[].file：这是本次该读的语言档案绝对路径
→ 拿到 rules.project：这是项目档案（如果有）
调用 svn_change_set
→ 拿到变更集：这就是本次允许修改的全部文件
```

**② 没装插件**：跑 `tools\run-audit.cmd`，产物在 `reports\review-packet.md`，
包尾的「审查指令」段已经写好了该加载哪几份档案。

> 无论走哪条路，**在读到语言档案之前，不要对 NPE、线程安全、版本语法发表意见。**
> 那三类意见是误报的主要来源。

## 0. 快速选择

| 我想要 | 用哪条 |
|---|---|
| 只审一遍，看有没有问题 | **命令 1** 只审不改 |
| 先看报告，再决定怎么修 | **命令 2** 出报告并修复 |
| 别废话，直接把代码改好 | **命令 3** 直接改不报告 |
| 第二轮、第三轮再看一遍 | **命令 4** 复审 |
| 改动很大，先看整体风险 | **命令 5** 风险概览 |

## 1. 命令 1：只审不改

适用：日常提交前过一遍，只要结论和问题清单。

```text
基于 SVN 中已经修改的代码，按 E:\rules\ai_code_review_files 下的规则做审查，只审不改。

1. 先跑 tools\run-audit.cmd，复述本次变更了哪几个文件
2. 读 REVIEW_RULES.md / SVN_WORKFLOW.md，按变更文件的扩展名读对应语言档案
   （.java→languages\java8.md，.cpp/.h→cpp.md，.js/.ts→javascript.md，.cs→csharp.md），
   有项目档案再读 projects\x_main.md，并读 REVIEW_RULES.md 附录 A 的裁决记录
3. 只审变更集内的 diff 行，变更集外的文件不审、不改
4. 每条 P0/P1 必须给出 ①②③④，给不出就降为 P2
5. 附"查证后排除的候选问题"，说明你验证过哪些看起来像问题但其实不是
6. 一次给完整结论：BLOCK / PASS_WITH_NOTES / PASS，并声明加载了哪些档案

本次需求：<一句话说明你要做什么，可留空>
已知取舍：<你有意为之的地方，可留空>
```

## 2. 命令 2：出报告并修复

适用：想知道每条问题怎么来的，再决定改不改。

```text
基于 SVN 中已经修改的代码，按 E:\rules\ai_code_review_files 下的规则审查，然后修复。

1. 先跑 tools\run-audit.cmd，复述本次变更了哪几个文件
2. 读 REVIEW_RULES.md / SVN_WORKFLOW.md，按扩展名读对应语言档案，有项目档案再读
   projects\x_main.md，以及附录 A 的裁决记录
3. 按 REVIEW_RULES.md §5 规定格式输出完整报告（含 ①②③④ 举证、加载了哪些档案、查证后排除的候选问题）
4. 报告出来后：P0/P1 直接改，P2 列出来等我确认，P3 不管
5. 只改变更集内的文件，变更集外的问题只报告不修改
6. 改完重跑 tools\run-audit.cmd，确认变更集没有扩大，给一份验收结论

本次需求：<一句话说明你要做什么，可留空>
已知取舍：<你有意为之的地方，可留空>
```

## 3. 命令 3：直接改，不写报告

适用：不想看分析，只想要改好的代码。

```text
基于 SVN 中已经修改的代码，按 E:\rules\ai_code_review_files 下的规则审查并直接优化改掉，不要写报告。

1. 先跑 tools\run-audit.cmd 确定变更集
2. 只动变更集内的文件，变更集外的文件一律不碰
3. 允许优化（补判空、提前返回、消除重复、整理异常分支、去掉冗余判断），但不得改变业务语义
4. 不得新增依赖、不得改 build.gradle 或构建脚本、不得改变更集外的类或接口
5. 判断不了是否该改的地方，保持原样不动
6. 改完重跑 tools\run-audit.cmd，确认变更集没有扩大

只回三段，每段一两行：
1. 改了哪些文件
2. 每个文件改了什么
3. 判断有风险但没动的点（没有就写"无"）

不要问题清单、不要 ①②③④ 举证、不要复述 diff、不要贴改后代码。
```

## 4. 命令 4：复审（第二轮及以后）

适用：改完了再提交一轮，避免重复返工。

```text
基于 SVN 中已经修改的代码，这是第 <N> 轮复审，按 E:\rules\ai_code_review_files 下的规则只审增量，不改代码。

上一轮结论：<BLOCK / PASS_WITH_NOTES>
上一轮已修：<R1、R2 ...>
上一轮已裁决豁免不修：<列出哪几条、理由是什么>

1. 先跑 tools\run-audit.cmd 看现在的变更集
2. 只审新增和修改的增量，不重复提已修过、已裁决的问题
3. 若确实发现上一轮漏掉的 P0/P1，单独说明为什么上一轮没看出来
4. 一次给完整结论：BLOCK / PASS_WITH_NOTES / PASS

本次需求：<可留空>
```

## 5. 命令 5：风险概览

适用：改动很大（十几个文件），先看整体再决定细不细审。

```text
基于 SVN 中已经修改的代码，按 E:\rules\ai_code_review_files 下的规则先给我风险概览，不要逐条展开，也不要改代码。

1. 先跑 tools\run-audit.cmd
2. 输出：变更文件清单、每个文件的改动性质（新增/修改/删除，改了什么）
3. 风险分布：P0/P1/P2 各几条，分别集中在哪类问题上
4. 标出必须细看的文件或函数，以及建议优先看的原因
5. 等我确认后再逐条审
```

## 6. 两个填空位怎么写

命令 1、2、4 里有 `本次需求` 和 `已知取舍`。填了准确率明显更高，**留空也能发**。

### 本次需求

一句话，说清"改了什么、为了谁"。

```text
本次需求：新增"连续推送礼包"活动，支持货币购买和直购两种，直购走 ChargeStrategy_5 回调。
```

### 已知取舍

把你有意为之、看起来像 bug 的地方先交代掉。这是减少误报最有效的一行。

```text
已知取舍：
- 两个活动类型共用同一个 Strategy 类，是项目惯例，ActType 由 ActivityType 构造时注入
- getConditionByLevel 缺配时返回空列表，属既有框架行为，本次沿用
- 这段循环里的 try-catch 是故障隔离，不要合并
```

写不出来没关系，AI 会当成待验证项去查证，只是多花点时间。

## 7. 为什么这么设计

| 要素 | 解决什么问题 |
|---|---|
| **基于 SVN 中已经修改的代码** | 把范围钉死在变更集内，杜绝"到处去改没动过的代码" |
| **先跑 run-audit.cmd，复述变更文件** | 第一步就确认范围，后面想跑偏都难 |
| **只审不改 / 直接改不报告** | 明确这一次要结论还是要代码，避免它自作主张 |
| **本次需求 + 已知取舍** | 补上审查 AI 缺失的上下文，这是误报的最大来源 |
| **①②③④ 举证** | 逼它证明问题真实存在，挡掉"可能会空指针"这类废话 |
| **查证后排除的候选问题** | 让你看见它验证过什么，而不只是结论 |
| **一次给完结论** | 防止挤牙膏（发现一条 → 你改 → 再看下一条） |
| **复审写清已修 / 已豁免** | 防止每轮重复提同样的问题 |

## 8. 你会收到什么

### 命令 1、2、4（要报告）

```text
【变更集】本次变更 N 个文件：M xxx、A xxx ...      ← 范围确认

【审查结论】PASS_WITH_NOTES
【diff 覆盖率】已完整检查全部 N 个文件（是）
【问题统计】P0=0  P1=0  P2=3  P3=1

【问题清单】 表格：级别 / 位置 / 问题 / ①②③④ / 是否需本次修改

【查证后排除的候选问题】  ← 重点看这段，能判断它是否真读了代码
【附录：范围外观察】      ← 不阻塞，不用管
```

**如果没看到"变更集"和"查证后排除"这两段，说明它没按规则执行，让它重来。**

### 命令 3（不要报告）

```text
【改动】3 个文件
- XxxActivityScript.java：补 getConditionByLevel 判空，合并重复的 status 判断
- EventManagementInventory.java：CPE 循环提到 charge 判断之前
- ActivityType.java：无改动（仅确认枚举唯一性）

【未动】R2 付费玩家是否该上报 CPE，属业务判断，保持原样
【范围】重跑审计确认：M=3 A=1，无新增文件
```

没有报告，只有结果。**如果这时你开始想追问"为什么这么改"，说明该用命令 1 或 2，而不是命令 3。**

### 命令 5（概览）

```text
【变更概览】12 个文件，共 +860 / -120 行
【风险分布】P0=0  P1=2  P2=5
  P1 集中在：扣费与发货顺序（3 处）、模板判空（2 处）
【建议优先看】XxxInventory.java:220-260、YyyScript.java:88
【下一步】确认后我按命令 1 逐条审
```
